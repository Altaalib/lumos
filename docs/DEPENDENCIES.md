# Зависимости

## Системные

| Что | Версия | Зачем | Обязательно? |
|---|---|---|---|
| Go | 1.24+ (собрано и протестировано на 1.24; в `go.mod` заявлено `go 1.24` как минимум) | сборка всех трёх сервисов | да |
| PostgreSQL | 14+ (протестировано на 16) | единственное хранилище, роль очереди задач между сервисами | да |
| [golang-migrate](https://github.com/golang-migrate/migrate) CLI | любая v4.x | применение SQL-миграций из `/migrations` | да, хотя бы разово |
| Docker + Docker Compose | любая современная | локальный Postgres одной командой (`make up`), опционально — полный деплой контейнерами (`docs/DEPLOYMENT.md`) | нет, можно поднять Postgres и без Docker |

## Go-модули (go.mod)

Прямые зависимости — четыре штуки, дальше по каждой: что делает и
можно ли/зачем заменить.

### github.com/jackc/pgx/v5

Драйвер PostgreSQL. Выбран вместо стандартного `database/sql` +
`lib/pq`, потому что даёт нативный доступ к `RETURNING` и
`FOR UPDATE SKIP LOCKED` без обвязки, плюс пул соединений (`pgxpool`)
из коробки. Используется во всех трёх сервисах через `internal/storage`.

### github.com/gotd/td

MTProto-клиент — единственная в экосистеме Go библиотека такого
уровня зрелости для работы с Telegram *от лица пользователя* (не
бота). Только через неё можно читать публичные каналы, куда бот не
добавлен администратором — это и есть причина, по которой reader
устроен сложнее analyzer/notifier: Bot API для чтения чужих каналов не
годится в принципе, обхода нет.

### github.com/go-telegram-bot-api/telegram-bot-api/v5

Обёртка над Bot API — для notifier'а, который наоборот работает от
лица обычного бота (это ему разрешено и даже нужно — уведомления шлёт
именно бот, а не личный аккаунт).

### github.com/joho/godotenv

Подхватывает `.env`, если он есть рядом с бинарником — чтобы не
объявлять переменные окружения вручную при каждом локальном запуске.
На проде не обязателен: переменные окружения, заданные напрямую
(systemd `EnvironmentFile`, Docker `env_file`), имеют приоритет и
работают одинаково что с этим пакетом, что без него.

### LLM — без отдельного SDK

Сознательное решение: `internal/analyzer/llm.go` реализован на чистом
`net/http` + `encoding/json` против формата Chat Completions API
(тот же, что у OpenAI). Ни одна SDK-библиотека для этого не
подключена — плюс в том, что один и тот же код работает с любым
провайдером такого формата, достаточно поменять `LLM_BASE_URL` и
`LLM_MODEL` в `.env`:

- OpenAI — `https://api.openai.com/v1` (дефолт)
- OpenRouter — `https://openrouter.ai/api/v1`
- DeepSeek — `https://api.deepseek.com/v1`
- Локальный Ollama — `http://localhost:11434/v1` (см. раздел про
  локальные модели в `docs/architecture.md`)
- Локальный vLLM — обычно `http://localhost:8000/v1`

Если понадобится провайдер с другим форматом API (например,
нативный Anthropic Messages API вместо OpenAI-совместимого) —
единственное место для правок: реализовать интерфейс `LLMProvider` из
`internal/analyzer/llm.go` (`AnalyzeImportance(ctx, systemPrompt,
userPrompt string) (bool, error)`) заново, остальной код analyzer'а
не меняется.

## Особенность go.mod: replace-директивы

В `go.mod` есть блок `replace`, переадресующий несколько модулей
(`gopkg.in/yaml.v3`, `golang.org/x/crypto`, `go.uber.org/zap` и другие
транзитивные зависимости gotd/td и pgx) на их зеркала на GitHub. Это
не костыль для какого-то конкретного окружения — такие зеркала
работают всегда, при любом доступном интернете, наравне с оригинальными
путями. Если `proxy.golang.org` и `gopkg.in`/`golang.org` доступны без
ограничений (обычная ситуация на большинстве машин) — эти строки ни на
что не влияют, кроме источника скачивания конкретных версий. Убирать
их не нужно.
