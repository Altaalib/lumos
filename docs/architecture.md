# Архитектура сервиса персонального фильтра новостей

## Идея

Сервис читает посты из 1-2 публичных Telegram-каналов через юзер-сессию,
прогоняет их через LLM на предмет "важности" по заданным критериям и
отправляет отобранные посты в личку через Telegram-бота.

Архитектура — микросервисная, без брокера сообщений (Kafka/RabbitMQ).
Роль очереди выполняет общая таблица в PostgreSQL: сервисы не общаются
между собой напрямую (без RPC/HTTP между собой), а координируются через
статусы записей в БД.

## Компоненты

### 1. Reader

- MTProto-клиент на базе `gotd/td`, работает под юзер-сессией (не ботом),
  т.к. читает чужие публичные каналы, куда бот не добавлен как админ.
- Работает по своему тикеру (например раз в N минут).
- Каждый цикл: смотрит чекпоинт по каналу (`read_checkpoints`), запрашивает
  у Telegram все сообщения с ID больше сохранённого, вставляет их в `posts`
  со `status = 'new'`.
- Из сообщения берётся только текст: `message.Text` для обычных постов
  либо `message.Caption`, если это фото/видео с подписью. Сами медиафайлы
  (фото, видео, документы, стикеры) не сохраняются и не скачиваются —
  для анализа важности нужен только текст.
- Если у сообщения нет ни текста, ни подписи (голая картинка, стикер без
  подписи и т.п.) — такой пост пропускается ещё на уровне reader'а и в БД
  вообще не попадает, анализировать там нечего.
- Вставка постов + обновление чекпоинта — в одной транзакции (см. раздел
  "Транзакции и чекпоинты" ниже).
- При падении процесса восстановление идёт от последнего сохранённого
  `last_message_id` — не потеряет и не задублирует посты (дубли всё равно
  отсекаются уникальным constraint'ом на уровне схемы).

### 2. Analyzer

- Забирает посты со `status = 'new'` (атомарный захват через
  `UPDATE ... RETURNING`, см. ниже).
- Критерии важности хранятся в отдельном текстовом файле рядом с
  бинарником (например `criteria.txt`) — обычный свободный текст на
  естественном языке, без строгой структуры (YAML/JSON не нужен). Файл
  читается при каждом цикле (или даже при каждом запросе — цена чтения
  файла ничтожна по сравнению с запросом к LLM), поэтому правка критериев
  — это просто отредактировать файл, без пересборки бинарника и без
  миграций БД.
- Промпт собирается программно как склейка: неизменная системная часть
  ("проанализируй пост и реши, важен ли он") + содержимое `criteria.txt`
  + текст конкретного поста. От LLM в промпте явно просится один короткий
  токен ответа (например "yes"/"no"), чтобы парсинг результата был
  максимально надёжным.
- Отправляет запрос в LLM (на старте — облачный API, т.к. локальную модель
  сервер не тянет по памяти).
- Записывает `importance` (boolean: true/false — отправлять пост
  пользователю или нет) и `status = 'analyzed'`.
- Внутри может использовать worker pool: пачка постов разбирается на N
  горутин, каждая дергает LLM параллельно (I/O-bound задача) с
  ограничением по числу воркеров (чтобы не упереться в rate limit
  провайдера).

### 3. Notifier

- Забирает посты, где `status = 'analyzed' AND importance = true`.
- Отправляет их в Telegram через Bot API (`go-telegram-bot-api` /
  `telebot`).
- После успешной отправки проставляет `status = 'sent'` — повторно эти
  посты не трогает ни один из сервисов.
- Свой тикер, желательно чуть чаще, чем у analyzer'а, чтобы важные посты
  быстро долетали до пользователя.

### Общий принцип связи

Три независимых бинарника, единственная точка соприкосновения — таблица
`posts` в общей БД. Каждый сервис:
- работает на своём тикере,
- берёт только своё непересекающееся подмножество строк по `status`,
- не знает о существовании других сервисов.

Плюсы: при падении одного сервиса остальные продолжают работать, посты
просто накапливаются в очереди до восстановления. Деплой и рестарт любого
сервиса не затрагивает остальные.

## Схема БД (PostgreSQL)

```sql
CREATE TABLE posts (
    id           bigserial PRIMARY KEY,
    channel_id   bigint      NOT NULL,
    message_id   bigint      NOT NULL,
    text         text        NOT NULL,  -- message.Text либо message.Caption
    created_at   timestamptz NOT NULL DEFAULT now(),
    status       text        NOT NULL DEFAULT 'new',
        -- 'new' -> 'analyzed' -> 'sent'
    importance   boolean,     -- null пока не проанализирован,
                               -- true/false — отправлять или нет
    analyzed_at  timestamptz,
    sent_at      timestamptz,
    UNIQUE (channel_id, message_id)
);

CREATE TABLE read_checkpoints (
    channel_id      bigint PRIMARY KEY,
    last_message_id bigint,
    last_read_at    timestamptz
);
```

Почему `UNIQUE (channel_id, message_id)`:
дедупликация на уровне схемы, а не на уровне логики приложения. Даже если
reader попытается вставить один и тот же пост дважды (пересечение окон
опроса), база сама отбросит дубликат через `INSERT ... ON CONFLICT DO
NOTHING` — никакая гонка в коде это не обойдёт.

## Транзакции и чекпоинты

Ключевой вопрос: что делать со временем последнего чтения, чтобы при
падении reader'а не потерять и не задублировать посты.

Решение — чекпоинт по `last_message_id` (не по времени): у Telegram
сообщения идут строго по возрастающему ID, поэтому "дай всё после ID X"
надёжнее, чем работа с временными метками (нет проблем с часовыми поясами
и точностью времени).

Вставка постов и обновление чекпоинта должны идти в одной транзакции:

```
BEGIN
  INSERT INTO posts (...) VALUES (...), (...), ... ON CONFLICT DO NOTHING
  UPDATE read_checkpoints SET last_message_id = X, last_read_at = now()
  WHERE channel_id = Y
COMMIT
```

Если этого не сделать, возможна ситуация: посты вставлены, но процесс упал
до обновления чекпоинта — при рестарте зачитаются те же сообщения повторно
(не страшно благодаря UNIQUE-constraint, но лишняя работа). Опаснее
обратная ситуация без транзакции — чекпоинт продвинулся, а посты не
записались — тогда это уже потеря данных. Транзакция исключает оба сценария.

## Атомарный захват записей (защита от гонок)

Паттерн для analyzer и notifier — не `SELECT`, потом `UPDATE`, а атомарный
захват одним запросом:

```sql
UPDATE posts SET status = 'processing'
WHERE id IN (
    SELECT id FROM posts WHERE status = 'new'
    LIMIT 20 FOR UPDATE SKIP LOCKED
)
RETURNING id, text;
```

Это гарантирует, что даже если когда-нибудь появится несколько инстансов
одного сервиса параллельно, конкретную запись возьмёт только один процесс.
Для текущего сценария (по одному инстансу на сервис) это не обязательно
уже сейчас, но закладывается как задел на будущее.

Уровень изоляции — стандартный Read Committed вполне достаточен: сервисы
работают с непересекающимися срезами по статусу, конфликтов между ними
почти не возникает.

## Конкурентность внутри сервисов (Go)

Классический worker pool на буферизированных каналах, применим прежде
всего в analyzer'е (I/O-bound работа с LLM API):

```go
jobs := make(chan Post, 100)
var wg sync.WaitGroup

for i := 0; i < numWorkers; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for post := range jobs {
            // запрос к LLM, запись результата в БД
        }
    }()
}
```

- Analyzer — есть смысл в пуле воркеров (параллельные запросы к LLM),
  число воркеров ограничивается rate limit'ом провайдера.
- Notifier — пул менее актуален, Telegram Bot API сам лимитирует частоту
  отправки сообщений.
- Reader — воркер скорее на канал (если каналов станет больше), чем на
  пачку сообщений — там один MTProto-клиент обслуживает опрос.

## Структура пакетов (черновой вариант)

```
/cmd/reader          — main.go сервиса чтения каналов
/cmd/analyzer        — main.go сервиса анализа важности
/cmd/notifier        — main.go сервиса отправки уведомлений
/internal/reader     — MTProto-клиент, работа с чекпоинтами
/internal/storage    — доступ к БД (pgx), общий для всех трёх сервисов
/internal/analyzer   — LLM-клиент, промпты, критерии важности
/internal/notifier   — Telegram Bot API клиент
/internal/config     — критерии важности, список каналов, токены (YAML/JSON)
```

## Технологический стек

- **Go** — три независимых бинарника (reader, analyzer, notifier)
- **PostgreSQL** — общая БД, роль очереди задач через статусы
- **pgx** — нативный Postgres-драйвер (быстрее database/sql, прямой доступ
  к `RETURNING`, `FOR UPDATE SKIP LOCKED` и т.д.)
- **gotd/td** — MTProto-клиент для чтения публичных каналов через юзер-сессию
- **go-telegram-bot-api / telebot** — Bot API для отправки уведомлений
- **LLM** — облачный API на старте (расход токенов минимален для короткого
  анализа постов); локальная модель (Qwen2.5 7B через Ollama) как опция
  при переезде на железо с 8GB+ RAM

## Открытые вопросы на будущее (не блокируют старт разработки)

- Прокси для выхода в сеть (HTTP-прокси с авторизацией либо системное
  проксирование через WireGuard/redsocks) — актуально при переезде сервиса
  на железо, где нужен стабильный внешний IP.
- Хостинг: домашний ноут (8GB RAM) через Tailscale, либо бюджетный VPS
  (Hetzner CX22 и подобные) с ~4GB RAM.
- Расширение на большее число каналов — тогда потребуется отдельный воркер
  на канал в reader'е и, возможно, пересмотр частоты тикеров.

## Порядок разработки

Логично двигаться последовательно, с проверкой на каждом шаге:

1. Схема БД + миграции (posts, read_checkpoints)
2. Reader — чтение одного канала, запись в БД, чекпоинты
3. Analyzer — анализ через LLM, простой промпт с критериями
4. Notifier — отправка ботом
5. Донастройка: worker pool в analyzer'е, конфиг критериев, второй канал
